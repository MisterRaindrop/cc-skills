# 向量化引擎共性问题库

每条的格式：**现象（候选信号）→ 类别 → 判定（需要哪些证据）→ 适用条件 → 修复方向**。
具体数字和出处在 `cases.md` 对应的编号下。

使用规则：
- 新问题先按"现象"对照。命中只说明"值得优先验证"，结论要按"判定"重新取证，至少两条独立证据。
- 条目中的数字阈值都是**案例值**，不是通用门限，换了数据规模或机器要重新标定。
- 新条目由报告第 12 步给出候选，人审核后再写入。

类别：A 参数 / B 计划 / C 引擎结构 / D 缺陷 / E 环境 / F 数据

## 内存类

### M1. 同步扫描把整个输出堆在 Sink 队列里
- **现象**：只做"扫表 → Motion"的 slice，内存一开局就到平台并一直保持；arrow 池峰值远小于 RssAnon；vmem 也看不到这部分内存。
- **类别**：C
- **判定**（需要两条）：
  1. 执行模式是 batch（start + wait，没有 yield，也没有线程池），可以看 debug1 日志或读 `execMain.c` 里的分支条件；
  2. 改变扫描节奏后平台消失或降低。例如在原型中加上同步扫描的 yield。这是因果证据。
  - 辅助证据：首次触碰的调用栈集中在 `ScanNode::StartProducing` 以下的 PAX 解码路径。注意它只说明"谁写入了这些页"，不能单独当作结论。
- **适用条件**：没有线程池的同步数据集扫描，且下游消费得比扫描慢。
- **修复方向**：同步扫描每 N 批让出一次，纯扫描 slice 默认走 yield 模式。

### M2. interconnect 队列参数放大了接收缓冲
- **现象**：接收 Motion 的 slice，单个 QE 的内存随 `gp_interconnect_queue_depth`、`gp_interconnect_snd_queue_depth`、`gp_max_packet_size` 增大而增大。
- **类别**：A
- **判定**：
  1. 会话级 A/B，只改这几个参数，看接收 slice 的 `peak_sum` 是否变化；
  2. 估算是否吻合：连接数 × 队列深度 × 包大小，和实测增量在同一个数量级。
- **适用条件**：接收方的消费速度跟不上发送方，队列被填满。
- **修复方向**：调回默认值，或按上面的公式估算后再设置。

### M3. 反压没有生效
- **现象**：上游远快于下游，中间队列持续增长。
- **类别**：A（开关没开）或 C（被保护逻辑关掉，或者结构上不支持）
- **判定**：在 debug1 日志里找 BP 和 VEC-YIELD-GUARD 两类记录，再对照下表找到对应的情况。

| 情况 | 反压 | 打开 `enable_vec_pipeline` 的效果 |
|---|---|---|
| 不带 CTE，本 slice 接收 ≤1 个 Motion | 默认关闭（开关默认 off） | 能启用反压，案例里能消除 OOM；但可能出现 C3 的小 batch CPU 开销 |
| 查询中任何地方带 CTE，或本 slice 接收 ≥2 个 Motion | 被 VEC-YIELD-GUARD 关掉，退回 batch 模式 | 不起作用；去掉 guard 强行走 yield 会有 S1 卡死的风险 |
| 没有线程池的同步数据集扫描 | `BuildSink` 不为它启用反压 | 不起作用，看 M1 / S2 |

- **修复方向**：第一种情况调参即可；后两种要修推模型（S1）或同步扫描（M1）。

### M4. 每线程一份的结构按机器核数预分配
- **现象**：小查询也很慢，耗时和行数几乎无关；空闲的 QE 就占几百 MB；CPU 火焰图里 memset 占比很高。
- **类别**：D
- **判定**：
  1. 扫一遍 `vector.pool_threads` 的取值，耗时或内存随它线性变化；
  2. 读代码确认：在 `StartProducing` 里按 `GetCpuThreadPoolCapacity()+1` 构造；没有 ExecContext 的 slice 用的是机器核数。
- **修复方向**：按需构造，或缩小初始容量。

### M5. 分配器保留：已释放的内存没还给系统
- **现象**：语句结束后 QE 的 RSS 仍然很高，但 arrow 池已归零；同一会话里的下一条语句在这个基础上继续涨。
- **类别**：C
- **判定**：先区分"保留"和"泄漏"。
  - **保留**：调用 `malloc_trim(0)`（gdb 中调用，属于 L3）或设置 `MALLOC_ARENA_MAX` / mmap 阈值之后 RSS 回落；同一语句重复执行时，RSS 在一个平台上稳定。
  - **泄漏**：trim 之后不回落；重复执行时每次都线性增长。这种情况转 D 类，去找没有释放的路径。
- **修复方向**：保留问题可以在语句结束时有条件地调用 trim，但这只是缓解，代价是下一次分配的开销。根本的办法是让大块内存走池或 mmap，或者换分配器。

### M6. 向量化内存在 vmem 之外
- **现象**：并发时 segment 被 OOM killer 杀掉（signal 9，没有 core），而不是某条查询收到 `Out of memory` 报错。
- **类别**：C
- **判定**：
  1. `dmesg` / `journalctl -k` 里有 OOM 记录，task_memcg 指向本集群；
  2. 同一时刻，vmem 记账远小于 RssAnon。
- **说明**：vmem 保护、`statement_mem`、资源组内存配额都基于 vmem 记账或算子内存预算，管不住不经过 vmem 的分配。并发数和 CPU 仍可以用资源组控制。机器级兜底只剩 cgroup 内存限制和 OOM killer。
- **修复方向**：所有分配都经过可统计的池，池外部分（PAX 缓冲、Sink 队列）也要纳入统计；再接入 vmem 或查询级内存上限（`vector.report_memory_to_vmem`、`vector.query_memory_limit_mb`）。

## CPU / 耗时类

### C1. sonicagg spill 抖动
- **现象**：高基数 HashAgg 比行引擎慢几倍；火焰图里缺页加 memset，或者重建哈希目录占了大头；spill 的写出和回读交替出现。
- **类别**：D
- **判定**：
  1. 预算被平分给各线程，每份很小；
  2. 扫一遍 spill 预算：加大预算只是推迟问题，行为形态不变。
- **修复方向**：按实际线程数分预算；驱逐时降到低水位为止，不要每个 chunk 都驱逐一次。

### C2. 表达式不短路
- **现象**：多个 OR / AND 组成的谓词，在不同表格式上慢的比例相同（说明问题和扫描无关）。
- **类别**：C
- **判定**：
  1. 读代码确认 `ExecuteScalarExpression` 先对整批算出所有参数再执行 kernel，运行时不短路；
  2. 把谓词改写成更有选择性的顺序或拆开后做 A/B，看耗时是否变化。
- **修复方向**：选择向量，或短路求值。

### C3. pipeline 模式下扫描输出小 batch
- **现象**：打开 `enable_vec_pipeline` 后 CPU 变多。
- **类别**：C
- **判定**：
  1. 对比开关前后每批的行数（用 uprobe 计数，或打日志）；
  2. 差分火焰图显示多出来的 CPU 落在每批固定开销的路径上。
- **修复方向**：合并 batch，或调整 pipeline 模式下的读取粒度。

### C4. 一阶段 agg 行数误估，Motion 搬运大量宽行
- **现象**：Redistribute 发送方的 slice 接近满载，大部分时间花在按目标拆分、序列化和 UDP 发送上。
- **类别**：B
- **判定**：
  1. EXPLAIN ANALYZE 里 group 数的估计值接近输入行数，实际值远小于此；
  2. 用 `optimizer_force_multistage_agg=on` 做 A/B。
- **修复方向**：自适应 partial agg（缩减比例差时直接透传）；不建议全局强制两阶段。

### C5. 扫描和发送串行，没有重叠
- **现象**：发送方 slice 先扫描一段时间，然后才开始发送；扫描期间接收方空闲。
- **类别**：C
- **判定**：
  1. 采样的 busy 时间段显示收发两侧交替忙；
  2. 多次抓栈或 off-CPU 分析显示，扫描阶段接收方停在接收等待上。
- **修复方向**：先按 M1 修复；之后再评估把扫描放到线程上、主线程负责发送带来的重叠收益。

## 卡住类

### S1. yield 模式下推数据源的顺序不受依赖约束
- **现象**：打开 pipeline 或 yield 后，带 CTE 或多个接收 Motion 的查询偶发卡住，CPU 接近 0。
- **类别**：C
- **判定**：
  1. 用 `stacks.sh` 抓 3 次以上：CPU 没有增长，栈也没有变化；
  2. 等待图成环：CTE 读端在 `shareinput_reader_waitready_vec` 等写端 → 写端停在 Motion 接收 → 对应的发送方又在等读端那个 slice；
  3. 去掉环上的一条边后卡住消失，比如关掉 yield。
- **修复方向**：
  - 在 yield 循环里加依赖门控，参照 DuckDB 的 pipeline 依赖；
  - 或者让 CTE 读和 Motion 接收在等待时让出，而不是死等，参照 DuckDB 的 BLOCKED 和 Velox 的 BlockingReason。

### S2. 同步扫描在暂停时卡死
- **现象**：没有线程池但打开了反压时卡住。
- **类别**：C
- **判定**：
  1. 多次快照里，唯一的线程都停在 `ScanNode::WaitIfPaused`；
  2. 这时没有其他线程能触发恢复。
- **修复方向**：同 M1，同步扫描在 yield 模式下应该返回，而不是阻塞。

## 环境与测量陷阱

### E1. 共享机器的污染
- 同机其他集群或容器的负载会改变 RSS、OOM 和耗时。测量时同时记录对方 cgroup 的 `memory.current`；OOM 用 `journalctl -k` 的 task_memcg 区分是谁触发的。

### E2. 测量陷阱
- 用 `grep` 找进程时会匹配到自己：先把 `ps` 输出写到文件再 grep，或者用 `qe_pids.py`。
- `perf record` 每次都写到一个新的临时文件，避免旧文件的属主或权限导致录到 0 个样本。
- `perf probe` 要用 `nm` 拿到的 mangled 名；匿名命名空间里的函数可能挂不上，要换一个能挂上的相邻函数。
- `perf stat -e` 中只要有一个事件不存在，整个命令就会失败。
- 用 `-g`（fp 回溯）采到的大部分帧是 `[unknown]`：构建没有帧指针，改用 `--call-graph dwarf`（flame.sh 默认就是 dwarf）。
- 在平台期抓 page-fault 会得到 0 个样本：新页面只在内存上涨阶段才会被首次触碰。
- 采样窗口要覆盖目标阶段：先看曲线，再决定 perf 抓哪一段。
- 冷缓存和热缓存不能混着比；A/B 顺序用 ABBA 交替。
- 一个进程从活跃变成空闲后，命令行会去掉 `cmdN sliceN`。按命令行分组时，要沿用它最初的 slice 标签（sampler 已经这样处理）。
